# 算法与调度接口联调说明

## 当前交付范围

已实现 CVRP-GA、VRPTW-GA、NSGA-II 预览、方案确认生成任务、开始/完成/取消状态联动。尚未完成前端地图、实时位置、逐站到达上报及全项目部署验收。当前完成任务会统一标记所有停靠点 arrived=true，这是任务级模拟完成，不是 GPS 到达证明。

本地 Swagger：http://localhost:3000/api/docs 。接口地址没有 /api 前缀，例如 POST /vrp/optimize。
localhost 指访问者自己的电脑，直接把这个网址发给组员，他们不能因此访问你的后端。优先让组员在自己电脑运行项目；若要同网联调，另行核对局域网地址、端口和网络环境。当前服务无登录鉴权，不应直接公开到互联网。

## 前端调用顺序

1. GET /orders、GET /vehicles、GET /drivers。选择 PENDING 订单、IDLE 车辆和 AVAILABLE 司机。编号必须来自当前数据库，不能在代码里固定为 1～6。
2. POST /vrp/optimize，显示预览；此步骤不分配资源。
3. CVRP/VRPTW 读取顶层 routes 和 solutionId；NSGA-II 读取 solutions，让用户选择其中一个 solutionId。status=NOT_FOUND 时不允许确认。
4. 为所选方案的每条路线绑定不同的司机，车辆必须与路线一致。
5. POST /vrp/confirm。成功返回 201 和 tasks，保存任务编号，并重新查询订单、车辆和司机状态。
6. PATCH /dispatch-tasks/{id} 开始/完成/取消，随后 GET 同一路径查看联动结果。

前端示例封装见 backend/demo/integration/logistics-api.mjs。导入文件不会自动发请求或创建任务。

## 预览示例

POST /vrp/optimize，Content-Type: application/json：

```json
{
  "algorithm": "NSGA-II",
  "orderIds": [4, 5, 6],
  "vehicleIds": [1, 2],
  "depot": { "lng": 116.4, "lat": 39.9 },
  "returnToDepot": true,
  "seed": 42,
  "departureTime": 480,
  "speedKmh": 30,
  "penaltyPerMinute": 1000
}
```

这组编号仅适用于当前演示库：任务 1 完成后订单 1～3 已送达，任务 2 取消后订单 4～6 待分配。使用前重新查询状态。换算法只需将 algorithm 改为 CVRP-GA 或 VRPTW-GA。

## 确认示例

POST /vrp/confirm：

```json
{
  "previewId": "替换为刚才响应里的实际 UUID",
  "solutionId": "solution-1",
  "assignments": [{ "vehicleId": 1, "driverId": 1 }]
}
```

上述 assignments 只是结构示例，必须按所选方案 routes 实际车辆填写；有两条路线就传两组不同司机的绑定。solutionId 也必须取本次返回值。

预览保存在后端内存中，15 分钟有效；重启失效，多进程部署尚需改造共享存储。确认时会重新检查订单、车辆和司机。点击确认后禁用按钮，避免重复提交；若网络中断，不盲目重试，先查询任务确认是否已创建。

## 配送状态

PATCH /dispatch-tasks/{id} 的请求体分别为：

```json
{ "status": "STARTED" }
```

```json
{ "status": "COMPLETED" }
```

```json
{ "status": "CANCELLED" }
```

| 转换 | 订单 | 车辆/司机 | 时间及停靠点 |
|---|---|---|---|
| ASSIGNED → STARTED | IN_TRANSIT | 保持占用 | 自动记录 startTime |
| STARTED → COMPLETED | DELIVERED | IDLE / AVAILABLE | 自动记录 endTime，全部 arrived=true |
| ASSIGNED/STARTED → CANCELLED | PENDING | IDLE / AVAILABLE | 自动记录 endTime，arrived=false |

已完成/已取消任务不能重新开始。重复提交相同状态不重置时间。不要提交 startTime/endTime，服务端自动记录。活动任务必须先取消才能删除。

## 单位与显示

- totalDistance（预览）和 totalDist（任务）：米，球面距离，不是道路里程。
- totalCost=null：未计算，不显示成 0 元。
- departureTime、arrivalTime、serviceStartTime：午夜起分钟数，480=08:00；输出可超过1440，应显示次日时间。
- startTime/endTime：真实接口操作时间，ISO UTC 字符串；前端按本地时区显示。
- 软时间窗：提前到达等待；服务开始超过窗口结束计算迟到；FOUND 只表示完整容量可行，不保证无迟到或全局最优。
- VRPTW penaltyPerMinute 是距离目标的等效惩罚，不是金额；NSGA-II 直接比较距离、车辆数、迟到三个目标。
- 地点坐标为 WGS84，经度 lng、纬度 lat。地图供应商坐标系不一致时需要转换，不能直接当作所有地图的坐标。

## 常见错误

| 响应 | 操作 |
|---|---|
| 400 | 查看 message；核对字段和状态。不要把优化参数传到 /vrp/distance-matrix |
| 409 | 资源/状态冲突或重复确认，刷新任务与资源列表后决定是否重新优化 |
| 410 | 预览过期或重启丢失，重新优化 |
| 连接被拒绝 | 检查后端是否启动，以及 API 地址是否指向正确电脑 |

GET 查询成功为200，confirm 创建成功为201；以 Server response 为准，不以文档静态 Responses 为准。

## 验收顺序

先只测试预览：选择当前 PENDING 订单 → 三种算法均返回可读方案 → 页面正确显示单位及候选方案。之后再安排一次明确的确认和配送模拟，检查车辆、司机和订单一起变化。

实验复现：在 backend 运行 pnpm.cmd run experiment:vrp，预期 PASS: 27 runs。报告在 backend/demo/algorithm-experiment/REPORT.md；它只覆盖合成样本求解器，不等于整个系统验收。
